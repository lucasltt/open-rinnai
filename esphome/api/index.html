API v1 · JSON

Documentação da API v1 · firmware 1.2.0. Os endpoints básicos existem desde 1.1.0. A coleção durável /sessions exige 1.2.0 e capabilities.completed_sessions. Confira a versão instalada.

Seu aquecedor, conectado.

Leia os sensores, acompanhe os usos e envie ajustes pela rede local. Esta API atende integrações próprias, um futuro visor remoto e ferramentas que entendam OpenAPI.

Endereço base · substitua o IP de exemplo pelo IP do seu ESP32http://192.168.1.50/api/v1

Leituras atuais

Comece por GET /state. Para um visor pequeno, GET /telemetry reúne a telemetria.

Verifique online e readings.*.stale. Uma temperatura ajustada ainda numérica pode ser antiga. null significa informação indisponível; não deve virar zero.

Sugestão: estado a cada 2 segundos; histórico, períodos e diagnóstico a cada 10 segundos ou mais.

Comandos confirmados

Envie POST com Content-Type: application/json e corpo de até 2048 bytes. Os campos e tipos devem corresponder ao contrato.

202 significa aceito, ainda em processamento. Consulte o estado do controle e compare boot_id e command_id com a resposta recebida.

A temperatura é um alvo absoluto de 35 a 50 °C. Um comando em andamento ocupa a fila; outro pedido pode retornar 409.

Consultar

GET/api/v1

Índice da API e caminhos disponíveis.

GET/api/v1/capabilities

Capacidades, limites e recursos suportados pelo módulo.

GET/api/v1/state

Estado completo: temperaturas, vazão, potência, chama, uso atual, consumos, configurações e avisos.

GET/api/v1/telemetry

Telemetria para consulta por outros dispositivos, com indicação de atualidade.

GET/api/v1/settings

Tipo de gás, tarifas, três favoritos e opções dos avisos.

GET/api/v1/control

Acompanhamento do último ajuste HTTP. Resultados: idle, queued, running, confirmed, failed ou cancelled.

GET/api/v1/history

Até 720 amostras compactas de 24 horas e 24 usos concluídos. As amostras ficam em RAM; os usos são preservados após reiniciar.

GET/api/v1/sessions

Desde 1.2.0: até 24 usos de um checkpoint confirmado na flash, mais antigos primeiro, com device_id, stream_id e ID por registro. Sem os pontos de gráfico; indicado para sincronização persistente.

GET/api/v1/periods

Resumos de até 31 dias e 12 meses. Datas em UTC−3; intervalos incompletos têm indicação de período parcial.

GET/api/v1/diagnostics

Comunicação, memória, armazenamento, inicializações e registro disponível da última falha.

GET/api/v1/health

Saúde do módulo: HTTP 200 quando os requisitos de comunicação e armazenamento estão atendidos; 503 quando indisponível.

Histórico por uso, com identidade durável

GET /sessions reúne somente os usos concluídos cuja gravação foi confirmada. Consulte a cada dez segundos ou mais. O ID de um uso é stream_id:sequence; horários e tarifas não fazem parte da identidade.

O cliente deve validar e salvar o snapshot antes de avançar seu cursor. HTTP 503, falha de disco ou conteúdo inconsistente mantêm o cursor anterior. Uma correção de relógio pode completar datas do mesmo registro, sem criar outro uso.

Os 24 registros do ESP são um buffer de recuperação. Se houver mais acionamentos durante uma desconexão, os antigos podem ser sobrescritos. Compare as sequências e sinalize lacunas; não invente os usos ausentes nem um início desconhecido.

pricing_basis=current_settings: custos desta resposta usam as tarifas atuais. Um arquivo permanente deve registrar a base de preço utilizada. A integração Rinnai Local conserva tarifas/custos da primeira importação, sem reprecificar o passado.

Água e gás separados

Os totalizadores, o uso atual e os resumos de períodos informam water_cost e gas_cost em R$. As parcelas usam o consumo estimado e as tarifas atuais; cost é a soma das parcelas disponíveis.

Uma parcela sem tarifa informada é null. Sem nenhuma tarifa, cost é null; com apenas uma, o total é parcial e cost_complete é falso. Consumo zero com tarifa configurada gera custo zero válido. Não há histórico de tarifas nem medidor físico de gás.

Controlar e configurar

POST/api/v1/temperature

{"target":38} · Temperatura inteira de 35 a 50 °C, verificada por leitura do aquecedor.

POST/api/v1/favorite

{"slot":1} · Aplica a temperatura do favorito 1, 2 ou 3 pelo mesmo controlador confirmado.

POST/api/v1/settings

{"gas_type":"GN","gas_tariff":0,"water_tariff":0} · Todos os campos são obrigatórios. Gás GN ou GLP; tarifas de 0 a 100000.

POST/api/v1/preferences

Substitui os três favoritos e as opções de aviso. Consulte o exemplo completo abaixo.

POST/api/v1/control/cancel

{} · Interrompe os próximos passos de um ajuste. Não desfaz um passo já transmitido.

POST/api/v1/device/restart

{"confirm":true} · Disponível após pelo menos 75 segundos desde o boot; antes disso retorna 503 com not_ready. Reinicia somente o ESP, após cerca de 500 ms. Durante uso de água ou ajuste em andamento, retorna 409. O limite aparece em limits.restart_min_uptime_s no GET /capabilities.

Após alterar tarifas ou preferências, consulte GET /settings para confirmar os valores persistidos. Não há comando HTTP de ligar/desligar o aquecedor nem envio serial arbitrário.

Corpo completo de preferências 
{
  "favorites": [
    {"name": "Banho", "temp_c": 38},
    {"name": "Conforto", "temp_c": 39},
    {"name": "Cozinha", "temp_c": 40}
  ],
  "alerts": {
    "long_use_enabled": true,
    "flow_enabled": true,
    "error_enabled": true,
    "offline_enabled": true,
    "long_use_min": 15,
    "continuous_flow_min": 20,
    "offline_seconds": 30
  }
}

Exatamente três favoritos; nome de até 31 bytes UTF-8 e temperatura de 35 a 50 °C. Todos os avisos e limites são obrigatórios. Limites de tempo: 1–180 minutos e 10–600 segundos sem resposta.

Exemplo de ajuste

Os exemplos abaixo são texto para seu cliente HTTP. Esta página não envia comandos.

curl http://192.168.1.50/api/v1/state

curl -X POST http://192.168.1.50/api/v1/temperature \
  -H 'Content-Type: application/json' \
  --data '{"target":38}'

curl http://192.168.1.50/api/v1/control

Guarde os identificadores da resposta aceita e acompanhe o controle até um resultado final. Só confirmed confirma o ajuste solicitado. Se uncertain for verdadeiro, um passo pode ter ocorrido sem confirmação. cancel_requested indica cancelamento ainda aguardando processamento.

Não repita automaticamente um comando após timeout. Leia o estado atual e o resultado do pedido antes de decidir sobre um novo ajuste. Os identificadores se referem ao último pedido HTTP e ao boot indicado.

Formato das amostras do histórico

As colunas de cada linha de samples estão listadas em sample_columns:

[age_s, inlet_c, outlet_c, flow_l_min, power_kw, heating]

Intervalos de 120 segundos. Temperaturas em °C, vazão em L/min e potência em kW. Timestamps dos usos são segundos Unix; um início desconhecido permanece null. Gás e custos são estimativas.

Home Assistant e visor

Para um visor próprio, use a API HTTP e respeite a atualidade de cada leitura.

A API nativa criptografada do ESPHome na porta 6053 expõe o número Temperatura ajustada, a ação ajustar_temperatura(target) e os sensores.

Para o histórico por banho/acionamento, a integração opcional Rinnai Local consulta /sessions e mantém os registros em armazenamento persistente do Home Assistant, com calendário e consulta paginada. Não depende de MQTT.

As integrações são instaladas/configuradas no servidor HA. A API HTTP está aberta na rede local; esta documentação não publica o dispositivo na internet.

Respostas e erros

200
Leitura disponível ou cancelamento sem ajuste ativo.
202
Pedido aceito para processamento.
400
JSON ou parâmetros inválidos.
403
Origem recusada.
404
Endpoint desconhecido.
405
Método não permitido.
408
Tempo esgotado ao receber o corpo.
409
Fila ocupada ou conflito com o estado atual.
413
Corpo maior que o permitido.
415
Tipo de conteúdo não suportado.
503
Módulo ou comunicação indisponível.

Erros incluem error, com mensagem legível, e code, para tratamento pelo cliente.
